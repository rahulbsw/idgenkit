# Benchmarks

How long it takes to generate one ID, in each library and database. For what IDs
cost once stored (index size, insert speed, compression), see
[Data engineering and storage](data-engineering.md). Those effects are usually
much larger than generation time: at 70 ns per ID, a million IDs take 70 ms to
generate.

Measured on an Apple M-series Mac (arm64, 14 cores), single-threaded unless
marked ×8. The databases ran in Docker (PostgreSQL) or natively (MySQL, Redis).
Rerun everything with `make bench`; the full report is in
[`bench/results/`](https://github.com/rahulbsw/idgenkit/tree/main/bench/results).

## Libraries

Nanoseconds per ID; lower is better.

|---|---|---|---|---|---|---|---|---|
| C core | 60 | 18 | 15 | 78 | 67 | 21 | 244 | 138 |
| Rust | 75 | 33 | 8 | 75 | 73 | 33 | 244 | 132 |
| Go | 124 | 48 | 16 | 258 | 121 | 51 | 244 | 297 |
| Java 24 | 256 | 29 | 36 | 149 | 284 | 28 | 244 | 254 |
| Python 3.12 | 1,333 | 422 | 2,468 | 1,896 | 1,766 | 868 | 411 | 1,279 |

Source: [`bench/results/2026-09-25-darwin-arm64.txt`](https://github.com/rahulbsw/idgenkit/blob/main/bench/results/2026-09-25-darwin-arm64.txt), generated by `bench/doc_tables.py`.

<!-- /bench-table -->

- **Snowflake is capped at 4,096 IDs per millisecond per generator** by its
  12-bit sequence, which works out to at least 244 ns per ID. Every native
  implementation reaches that ceiling. To go faster, add generators with
  different machine ids.
- **Random IDs cost one call to the OS random source.** That call dominates
  ULID, UUID and Nano ID timings. The monotonic generators are faster because,
  within a millisecond, they only increment the previous value.
- **On macOS the call gets about 6 times slower above 10 bytes** (≈ 40 ns up
  to 10 bytes, ≈ 230 ns above). The C core and Rust ask for at most 10 bytes at
  a time, so UUIDv4's 16 bytes cost about the same as UUIDv7's 10. Go's
  `crypto/rand` doesn't split requests, which is why Go's UUIDv4 and Nano ID
  cost about twice its UUIDv7.
- **Java's UUIDv4 is the JDK's `UUID.randomUUID()`**, which uses the faster
  `NativePRNG`. UUIDv7 and ULID use a per-thread `SecureRandom` DRBG instead, to
  avoid contending on one lock when many threads generate IDs.
- **Parallel generation on macOS contends on the system random source.**
  Generating ULIDs on all 14 cores in Go reaches 2.9 million per second in
  total, fewer than the 8 million a single thread manages. Linux's `getrandom`
  scales better here.

## Databases

Source: [`bench/results/2026-09-25-darwin-arm64.txt`](https://github.com/rahulbsw/idgenkit/blob/main/bench/results/2026-09-25-darwin-arm64.txt), generated by `bench/doc_tables.py`.

<!-- /bench-table -->

- **PostgreSQL** figures are `SELECT count(expr) FROM generate_series(1, 1e6)`
  minus the cost of `count(n)` alone. Snowflake's net figure can read below the
  244 ns cap because some of that overhead overlaps with waiting for the next
  millisecond; its wall time (287 ms per million) respects the cap. The UUIDv7
  columns are idgenkit's `uuidv7_generate()`, which works on 14+; the built-in
  `gen_random_uuid()` (UUIDv4) took about 8 times as long in this run. See the
  insert timings on the [storage page](data-engineering.md) for what each format
  costs once stored.
- **MySQL** figures use `BENCHMARK(1000000, expr)` on one connection. MySQL's
  `UUID()` returns version 1 UUIDs (time based), which are cheap to generate.
- **Redis** throughput is bound by networking and command dispatch (50 clients,
  pipeline depth 16): every command runs at `PING` speed.
